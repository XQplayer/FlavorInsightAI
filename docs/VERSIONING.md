# 版本与归档规则

## 两条软件记录

- `FlavorInsight AI 1.0.0`：历史汇总与冻结快照，标签 `flavorinsight-v1.0.0`。
- 原 FlavorThresholdDB `v1.*` 标签属于旧编号，原样保留；不要挪动旧 `v1.1.0` 来表示新平台。
- 新平台后续版本使用 `flavorinsight-v*` 标签；重新编号不是对旧版本做 SemVer 降级比较，也不是退回旧功能。

## 一致性

根目录 `VERSION` 是交付构建版本的依据。前端包、首页、Render 配置及发布工作流必须同步；代理 `/health` 的 `api_version` 保持原字段名但返回实际源码构建版本，不再由可能过时的 `API_VERSION` 环境标签覆盖。该字段用于构建溯源，不改变接口协议。

GNPS 索引、数据库清单、文件格式、模型与统计引擎自身的版本独立管理，不随应用版本机械替换。历史计划、审计和验证记录中的旧号是当时证据，不全局替换。

## 发布顺序与回退

1. 完整备份原发布元数据、原文、原文档和 Git 标签对象/提交 SHA。
2. 验证新的源码、CI、Pages及代理实际构建版本；发布新的当前版本和历史归档，附小型备份文件。
3. 检查替代发布和资源后，仅将已批准的五个旧软件 Release 转为草稿；不删除 Release、不删除或移动标签。
4. 数据资源发布继续公开，仅明确名称中的数据资源身份，附件不动。

回退时按备份恢复旧 Release 的可见性、名称/原文及 Latest 标记，并撤销本次代码合并后重新部署。GitHub可能在重新公开时产生新的发布时间；原始日期始终保存在备份。旧源码和提交不依赖 Release 可见性，不受影响。
