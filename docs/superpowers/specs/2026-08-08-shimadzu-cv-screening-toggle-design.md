# 岛津 GC-MS CV 筛查开关设计

## 目标

将 CV 筛查从固定执行改为分析前可选功能，并允许用户设置 CV 阈值。未启用时仍计算 Mean、SD、CV，但不进行 CV 过滤，也不生成筛查后结果。

## 用户界面

在岛津分析页面的“运行设置”区域增加一个 CV 筛查设置块：

- 复选框：`启用 CV 筛查`，默认不勾选。
- 数值输入：`CV 阈值 (%)`，默认 30，范围 0–1000，步长 1，允许用户手动输入小数。
- 未勾选时输入框禁用，并显示“仅统计，不筛查”。
- 勾选后输入框启用，并显示“超过该阈值的平行结果将按现有规则筛查”。
- 运行前对阈值进行校验：必须是有限数值，且处于 0–1000 范围内；非法值阻止开始分析并给出原因。

开始分析时，将 `enableCvScreening` 和 `cvThreshold` 固定写入当前任务配置、浏览器任务恢复数据和云端任务的 `source_names`/运行摘要，保证刷新恢复和报告可追溯。

## 计算流程

页面 → Worker Client → Web Worker → `runShimadzuBrowserPipeline` → `stage5`：

1. 页面在提交前读取开关和阈值。
2. Worker 启动消息携带两个参数；恢复任务使用保存的同一组参数，不读取当前页面后来改变的值。
3. `stage5` 始终计算 Mean、样本 SD 和 CV。
4. `enableCvScreening = false` 时，统计结果保留全部浓度，筛查后表与筛查报告为空或明确标记为未执行，不删除数据。
5. `enableCvScreening = true` 时，沿用现有 `processV2Statistics` 的 CV 判定规则，以用户阈值替代固定 30，生成筛查前后结果、筛查报告和矩阵拆分结果。
6. `stage5` 的 `qcRows`、`data.json`、manifest 和计算报告记录是否执行筛查及实际阈值。

科学计算核心的 Mean、SD、CV 算法和已有 CV 判定算法不改写；仅将固定阈值和筛查动作变为显式配置。

## 输出契约

无论是否启用筛查，都保留：

- 三平行浓度；
- Mean 浓度与样本 SD；
- CV 数值；
- `CV_Screening_Executed` 状态；
- `CV_Threshold` 实际阈值；
- 质量报告和处理日志。

未启用时，筛查后输出不作为有效筛选结果使用，并在工作簿和报告中标记 `NOT_EXECUTED`，避免把“未筛查”误读成“全部通过”。

## 错误处理与恢复

- 阈值校验在创建任务前完成，不产生半成品任务。
- 任务恢复时优先使用任务保存的 CV 参数。
- 参数缺失的旧任务兼容为 `enableCvScreening = true`、`cvThreshold = 30`，保持历史结果一致；新任务默认关闭筛查。
- 失败任务、部分结果 ZIP、云端任务记录继续保留 CV 参数和执行状态。

## 验证

- Worker 测试：未启用时不筛查；启用时使用自定义阈值。
- 页面静态测试：开关默认关闭、阈值输入范围/步长、开始任务传参和文案存在。
- 输出测试：两种模式均能生成可打开的 Stage 5/6 工作簿，并记录执行状态。
- 回归测试：现有 Shimadzu 核心、浏览器流水线、云端任务和构建测试全部通过。
