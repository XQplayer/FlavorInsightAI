# Development workflow

1. **Intake:** read `AGENTS.md`, relevant README/design docs, current branch/status, affected code and tests. Identify raw-data, auth, deployment and scientific boundaries.
2. **Contract:** state inputs, outputs, dependencies, errors and acceptance criteria. For scientific computation, identify source rows, sample/group semantics, units, exclusion rules and approved reference values. Resolve scientific-rule ambiguity before changing formulas.
3. **Route:** apply the canonical `SKILL_ROUTING.md`: one of six primary domains plus L1–L4 impact, with only triggered cross-cutting specialists. Use Superpowers as the single process. L3/L4 work uses an isolated worktree from the intended baseline when needed; keep existing uncommitted changes intact. `UNIFIED_SKILL_ROUTING.md` is the short entry point and does not override this policy.
4. **Baseline:** capture current behavior and hashes. Reference-value fixtures must be independent of the implementation; if truth is uncertain, call it a behavior baseline. A failed existing check is recorded before edits.
5. **Implement:** keep diffs small and reuse modules. For bugs, reproduce and locate the cause. Preserve original data and transformation lineage.
6. **Verify:** run the affected checks in `QUALITY_GATES.md`, inspect outputs, and record exact commands and results. Browser and manual checks are distinct from unit tests; local pass is distinct from matching remote Actions run. If a Skill or required tool is unavailable, record the fallback and the quality checks retained.
7. **Review:** inspect diff against the contract and scientific boundaries. Dispatch an independent reviewer for full work when available, or record a serial self-review.
8. **Deliver:** list chosen route/level, Skills actually read, roles actually dispatched, changed files, test evidence, open issues and rollback steps. Do not push, create a PR, merge, deploy, mutate production data, or change secrets without authorization for the corresponding operation.

For phase 3 and later work, separate four decisions at delivery: local engineering checks, dependency risk disposition, scientific reference coverage, and a matching remote CI run. A historical Actions run or a nonblocking audit is not a passing deployment gate. Record the exact Skill files actually read and the task behavior they changed; a routing table alone is design evidence. For any new scientific formula, commit a synthetic or approved reference fixture with units, hand/independent calculation, tolerance, failure cases and source before changing the algorithm. Keep unverified legacy methods labeled pending. L4 risky execution waits for separate authorization after safe local preparation; no default production release.
